# The collector

Part of the [style guide](../README.md). How the worker (`src/worker.ts`, `modules/collector`) pulls the Lesta API into TimescaleDB. Overview: [apps/web/server/CLAUDE.md](../../../apps/web/server/CLAUDE.md).

## Rules of the worker

- **Queue contracts live once**, in `modules/collector/contracts` (`QUEUE`, `JOB`). Processors parse every payload with its schema; the API enqueues through `CollectorProducerService`. A module that owns its own queue (discord, streamers, notifications, progression, competitions, …) keeps that queue's name, job names and payload schema in its own `config/` — never a string literal at a call site, and never the collector barrel imported from another worker module (import cycles).
- **Every processor wraps its work in `MetricsService.track({ job, run })`**, which counts the job and attributes the Lesta calls made inside it to the job's queue. A processor extends `TrackedWorkerHost` (`modules/collector/metrics`), whose `process(job)` runs the processor's protected `handle(job)` inside `track`; one that must act before tracking (the sweep's breaker delay) extends `WorkerHost` and calls `track` itself. A module outside the collector imports `TrackedWorkerHost` and `MetricsService` from `modules/collector/metrics` (global, cycle-free), never from the collector barrel.
- **Collector sub-modules**: `tracking`, `clans`, `reference`, `aggregates`, `news`, `purge` (processors), `metrics`, `producer`, `queues`, `schedules`, `board`, `monitoring` (infrastructure) — each shaped like a module; one with a single service keeps it at its root.
- **Lesta goes through `core/lesta`**: `priority` for tier A and the API, `bulk` for sweeps, sharing one Redis bucket (`LESTA_RPS`) with the bulk lane capped at `1 - LESTA.tierAReserve`. With several registered IPs each process names its egress in `LESTA_EGRESS_IP` (one of `LESTA_EGRESS_IPS`, at most 5) and gets its own bucket pair, so `LESTA_RPS` is always the budget of one IP. The breaker (`metrics/services/circuit-breaker.service.ts`, cockatiel `SamplingBreaker`) only observes outcomes; while it is open the sweep worker pauses and sweep batches are delayed.
- **Schedules** are `modules/collector/schedules/config`, on unless a schedule sets `enabled: false` (only `FEATURES.moePoliroid` does today) and off under `NODE_ENV=test`; `runOnBoot: true` (the `moe-estimate` job) also fires the job once on every worker boot (BullMQ `immediately`), so a deploy fills what the cron would otherwise wait a day for. Without `LESTA_APPLICATION_ID` the worker starts degraded, in every environment: it logs a warning, loads no tracking or clan processors and registers no Lesta schedule. Every module registers its schedules through `createJobSchedules` (`common/schedules`) in Moscow time (`TIME.zone`); a scheduler whose id is no longer configured on its queue is removed on boot.
- **Lanes and retries**: each lane queues on its own in-process limiter queue (`LESTA.request` / `LESTA.bulk`) against the same Redis buckets, so a sweep backlog never overflows the priority lane; a full local queue throws `LestaQueueFullError`, which is retryable. The bulk lane retries once inside the client and leaves the rest to BullMQ's job backoff. Failed jobs are kept a week for post-mortems but capped by count, so an outage that fails every poll cannot grow Redis (noeviction) without bound.
- **Marks on gun**: when the achievements call for an account succeeds, the poll writes the Lesta value (0 included) for every tank it reported and stamps `player_tank.marks_source = 'lesta'`; a mod report that changes the value stamps `mod`. The marks leaderboard counts only `lesta` marks.
- **Mod data in public aggregates**: per-battle caps (`MOD_BATTLE_LIMITS`) bound every mod-reported stat; tank economy, mode meta and the MoE curve publish a value only when `MOD_AGGREGATES.minAccounts` distinct accounts feed it; `corroboratedBattleSql` (public feeds, competitions, challenges, honest RNG) needs a Lesta delta for a random battle or a replay of the same battle uploaded by someone other than the account's owner, for every mode, while `ownerTrustedBattleSql` keeps the owner's non-random battles on the owner's own pages.
- **Polling one account**: Lesta is read outside the database; the write phase (latest snapshots, new snapshots, deltas, `player_tank`, marks, the API day session) runs in `lockedTransaction` scoped `poll` per account, so enrol, poll and sweep never write the same battles twice. `tank_snapshot_latest` holds the last snapshot per tank and mode outside the hypertable, so retention never loses a tank's totals; it is the delta base and part of the overall rating.
- **API day sessions**: every write with deltas rebuilds `play_session {source: 'api', kind: 'day'}` for that Moscow day from the day's random-mode `tank_battle_delta` rows (idempotent upsert on `(account, source, kind, day)`); leagues, weekly challenges, the watchlist digest and the competition fallback read them. They are a rollup, not a play session: session reports and the `session.ended` webhook read only `kind: 'live'` sessions (the mod's), so a day is never announced twice. `mark.gained` is collected inside the account transaction and emitted only after it commits (dedupe key `markGainedKey`), so a rolled-back poll announces nothing and the lock never waits on Redis or a second pool connection.
- **Pool size**: the worker's pool is `WORKER_DATABASE.poolMax` (tracking jobs × accounts per job + the other queues + headroom); `DATABASE_POOL_MAX` overrides it per process.
- **Deletion requests** (`data_deletion_request`, source `user` or `lesta`): deleting a site account opens a `user` request for every linked Lesta account in the same transaction; Lesta's requests go through `bun run deletion:request --account <id> --reason "<ticket>"` (`scripts/deletion-request.ts`). Opening one hides the player (`is_hidden`) and revokes the account's mod devices at once; the `purge` dispatch then deletes the account's hypertable rows (each `DELETE` on its own) and the relational rows in one transaction — including the replays the account recorded (their files go after the commit) — and replaces the account with an anonymous placeholder (`PURGE.anonymousReplayName`, no account id or clan tag) in the summaries of other people's replays, which the replay view then leaves out. A request in any status but `superseded` blocks collection (`PurgeGuardService`: the collector, clan sync, `PlayerResolverService.ensure`, search discovery, the garage sync (hidden players), `/mod/ingest` and `/mod/bind` (403 `device_revoked` / `account_mismatch`) all skip or refuse it); a purge that fails goes back to `pending` until its last attempt, then `failed`, and is dispatched again after `PURGE.failedCooldownMs`. A request left `processing` by a crashed or stalled job is dispatched again on every run; the job id `purge-<request id>` keeps a live run from doubling. Re-link after deletion: signing in with Lesta ID again is new consent, so `LestaAccountsWriterService.link` calls `PurgeGuardService.liftUserRequests` inside its transaction — every `user` request of the account becomes `superseded` (`superseded_at`), and when no `lesta` request stands the player is unhidden, set `active` and enrolled; a `lesta` request stays in force (the link is written for sign-in, the player stays hidden and untracked, no nickname history). An in-flight purge is cancelled, not raced: the job claims its request (`PURGE.claimableStatuses` → `processing`) and skips a superseded one, and its relational transaction first closes the request (`processing` → `completed`, row-locked against the re-link) and keeps every relational row when that finds it superseded; hypertable rows already deleted stay deleted, and a failure never overwrites `superseded`.
- Data retention is a Lesta term: the purge jobs, the generic retention job (`RETENTION` in `purge/config`, batched deletes per table; revoked `mod_device` rows go 30 days after `revoked_at`) and the Timescale policies (`config/timescale.constants.ts`) are not optional.

## Without a Lesta key

There is no Lesta mock and no generated data, in development either. An empty `LESTA_APPLICATION_ID` means no Lesta: the worker runs degraded (above), `/auth/lesta/start` redirects back with `lesta_not_connected` instead of opening Lesta ID, `/health` reports the worker as degraded, and every endpoint answers with empty data. `bun run gamedata:import` still loads the vehicle catalog, maps and missions from the public client-data repositories (in production: `docker compose run --rm server bun scripts/gamedata-import.ts --cache /tmp/otmetki-gamedata`, docs/ops/deploy.md).
